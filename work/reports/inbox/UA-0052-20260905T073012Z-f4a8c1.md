# Worker report UA-0052

## Summary

Fixed all four UA-0048 findings with regression tests; no scope creep beyond the listed files.

- **R1** (`content-contract.ts`): `status` carried `.default('draft')` on the shared field definition, so `updatePostInput.partial()` still injected `status: 'draft'` into a PATCH that omitted it, both silently unpublishing on a title-only edit and defeating the "at least one field" check on a timestamp-only PATCH (the synthetic default field always counted as "present"). Moved the default onto `createPostInput` only (`postFieldsSchema.extend({ status: postStatusSchema.default('draft') })`); the base field is now a plain required enum, so `.partial()` leaves `status` genuinely absent when omitted. Verified via `node -e` against installed Zod 4.5.4 that `{...existing, ...input}` merges now retain `existing.status`, and that an omitted key no longer appears in the parsed object at all (`'status' in parsed === false`).
- **R2** (`content-contract.ts`): the cover-URL refine only checked an `https?://` prefix, so `'https://'` passed but `new URL(...)` in `seo.ts`'s document renderer throws on it (confirmed: `new URL('https://', origin)` throws `Invalid URL`). The refine now also does `new URL(value).hostname` in a try/catch and requires a non-empty hostname.
- **R3** (`router.ts`): the direct `authentication().api.getSession({ headers })` call discarded Better Auth's renewed `Set-Cookie` (confirmed via better-auth's own `dispatch.mjs`/`types/api.d.mts` that `returnHeaders: true` returns `{ headers, response }`). `admin()` now takes a `sessionHeaders: Headers` collector, appends any `set-cookie` from that result, and both call sites (`/api/admin/*` and the SSR `/admin*` guard) pass it through; the router's outer wrapper creates one collector per request and appends it onto the final response headers after `dispatch()` resolves (so it's still applied on caught errors, e.g. a 403 after a renewed-but-non-admin session).
- **R4** (`request.ts`): the over-limit branch awaited `reader.cancel()` before throwing; for a chunked (no Content-Length) body, that await could hang past the client's timeout (reproduced by the audit). Replaced the blocking cancel with a non-blocking background drain (`drainInBackground`) that keeps reading and discarding until the stream ends, then releases the reader lock, so the 413 throw is never blocked on it. Also applied the same drain to the previously-untouched declared-Content-Length-over-limit branch: an isolated repro (`tmp-*.mjs`, deleted after use) showed that on a reused keep-alive socket, a declared-oversized body that's *never drained at all* corrupts the next pipelined request  (~5s stall then `ECONNRESET`), which the existing single-request-per-test suite had never exercised. Considered forcing `Connection: close` on the response instead (matching the audit's "safe connection disposal" wording) but proved experimentally that closing while the client is still mid-write of a large body causes an immediate `ECONNRESET` on the client's own oversized request; draining in the background (Node's own body framing then lets the connection reuse safely) avoids that class of bug entirely and needed no node-adapter.ts change.

## Regression tests added

- `tests/server/content.test.ts`: schema-level checks that a partial update never synthesizes `status`, and that `'https://'` is rejected while a normal absolute URL passes.
- `tests/server/runtime.integration.test.ts` (real PGlite + Better Auth): title-only PATCH keeps a published article public and returns `status: 'published'`; timestamp-only PATCH is rejected (400); malformed cover URL is rejected at create time (400, never persisted); session aged past its refresh threshold (`expires_at = now() + interval '6 hours'` against the real `session` table, matching better-auth's own `shouldBeUpdated` formula) gets a forwarded renewed cookie on both `/api/admin/session` and the SSR `/admin` page.
- `tests/server/node-adapter.test.ts` (real loopback Node HTTP server): declared-oversized and chunked-oversized bodies both return a prompt 413 (no timeout), and a follow-up request on the same reused connection still succeeds in both cases, proving the drain fix rather than just closing the connection.
